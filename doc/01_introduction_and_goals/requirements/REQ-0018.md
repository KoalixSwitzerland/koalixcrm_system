# REQ-0018: Das System verwaltet eine workspace-isolierte, n-stufige Lagerort-Hierarchie mit typisierten Knoten und Barcode-Adressierung

## Lizenzseite
Open-Source-Backend (`/app/koalixcrm`)

## Quelle
ADR-0009 (Lager-Domänen-Backbone)

## Why
Lagermitarbeiter müssen jeden Stellplatz eindeutig und maschinenlesbar adressieren können, um
Kommissionierfehler zu vermeiden; ohne eine strukturierte, beliebig tiefe Standorthierarchie mit
Barcode-Auflösung ist weder eine AS/RS-Adresse noch ein einfacher Regal-Fach-Ebene-Position-Pfad
referentiell abbildbar.

## Beschreibung
`Location` (workspace-scoped) ist ein Knoten in einer n-stufigen Standorthierarchie mit einem
rekursiven Selbstverweis auf einen optionalen Elternknoten: „Eine n-stufige `Location`-Hierarchie
mit einem einzelnen rekursiven Selbstverweis ... ermöglicht beliebige Tiefe (Warehouse → Zone →
Gang → Regal → Fach → Bin) ohne Schema-Änderung" (ADR-0009). Jeder `Location`-Knoten trägt einen
`location_type` aus dem Enum `WAREHOUSE`, `ZONE`, `AISLE`, `RACK`, `SHELF`, `LAYER`, `BIN`,
`VIRTUAL`, `CUSTOMER_SITE` (ADR-0009, Amendment 2026-05-04: „Der `location_type`-Enum wird um den
Wert `LAYER` erweitert, der zwischen `SHELF` und `BIN` eingeordnet ist").

Jeder Knoten trägt eine mandanteneindeutige Kurzbezeichnung (`code`), einen Namen (`name`), einen
optionalen Adress- oder Barcode-Klartext (`external_ref`) und ein Aktiv/Inaktiv-Flag (`is_active`).
`external_ref` ist die Grundlage für die Barcode-Auflösung eines Stellplatzes: „`external_ref`
(optionaler AS/RS-Adressstring oder Barcode-Klartext)" (ADR-0009).

Globale Lookup-Werte (die `location_type`-Enum-Werte selbst) sind plattformweit stabil und als
Enum im Code gepflegt, nicht workspace-gebunden: „`LocationType`-Enum-Werte | global | Typen sind
plattformweit stabil; kein mandantenspezifischer Bedarf; als Enum im Code" (ADR-0009). `Location`
selbst ist workspace-scoped und erbt den `WorkspaceScopedModel`-Mechanismus: "Tenant-owned data
inherits `WorkspaceScopedModel` and is filtered by `request.active_workspace`" (ADR-0001).

## Acceptance Criteria

### AC-1: Location-Grundstruktur
- [ ] `Location` trägt einen nullable FK `parent` auf sich selbst, ein `location_type`-Feld aus dem Enum `WAREHOUSE`, `ZONE`, `AISLE`, `RACK`, `SHELF`, `LAYER`, `BIN`, `VIRTUAL`, `CUSTOMER_SITE`, einen `code`, einen `name`, ein optionales `external_ref` und ein `is_active`-Boolean-Feld.
- [ ] `code` ist innerhalb eines Workspace eindeutig.
- [ ] Ein `Location`-Knoten ohne `parent` ist ein gültiger Root-Knoten.
- [ ] Ein `Location`-Knoten mit `parent`, der auf eine `Location` außerhalb desselben Workspace verweist, wird vom System abgewiesen.

### AC-2: Beliebige Hierarchietiefe
- [ ] Das System erlaubt eine `Location`-Kette beliebiger Tiefe über den rekursiven `parent`-Selbstverweis, ohne Schema-Änderung.
- [ ] Eine zirkuläre Eltern-Kind-Beziehung (ein Knoten ist direkt oder transitiv sein eigener Vorfahre) wird vom System abgewiesen.
- [ ] Eine Abfrage des vollständigen Pfads eines `Location`-Knotens bis zum Root-Knoten liefert alle Vorfahren in der Reihenfolge vom Root zum angefragten Knoten.

### AC-3: Adressierung und Barcode-Auflösung eines Stellplatzes
- [ ] `Location.external_ref` ist ein optionales Textfeld, das einen AS/RS-Adressstring oder einen Barcode-Klartext aufnimmt.
- [ ] Ist `external_ref` gesetzt, ist es innerhalb des Workspace eindeutig.
- [ ] Das System liefert für einen gegebenen `external_ref`-Wert und Workspace genau einen passenden `Location`-Datensatz oder keinen Treffer.

### AC-4: Aktiv/Inaktiv
- [ ] `Location.is_active` ist standardmäßig `true`.
- [ ] Ein `Location`-Knoten mit `is_active = false` bleibt in der Hierarchie bestehen und ist über den `parent`-Pfad weiterhin traversierbar.
- [ ] Das System weist die Anlage eines neuen `OnHandRecord`-Eintrags (REQ-0019) an einer `Location` mit `is_active = false` ab.

### AC-5: Workspace-Isolation
- [ ] Jede Datenbankabfrage auf `Location` filtert automatisch nach `workspace`.
- [ ] Ein automatisierter Test verifiziert, dass `Location`-Einträge aus Workspace A nicht in Abfragen aus Workspace B erscheinen.

## Quality Attributes
- **Datenintegrität**: Ein `Location`-Knoten mit `parent`-Verweis auf einen nicht existierenden oder workspace-fremden Elternknoten wird vom System abgewiesen; zirkuläre Referenzen sind ausgeschlossen.
- **Performance**: Die Traversierung des vollständigen Pfads eines `Location`-Knotens bis zum Root über eine 4-stufige Hierarchie (Regal → Fach → Ebene → Position) liefert das Ergebnis in einer einzigen Datenbankabfrage (rekursive CTE), nicht in einer Abfrage je Hierarchieebene.

## Betroffene Komponenten
- Backend: `koalixcrm/stock/models/location.py`, `location_type`-Enum, rekursive Pfad-Abfrage (CTE oder äquivalente ORM-Erweiterung), DRF-Serializer und ViewSet
- Frontend: Lagerort-Verwaltung (Baumansicht, Anlage/Bearbeitung eines Stellplatzes) über DRF-Endpunkte
- Deployment: keine Infrastrukturänderung

## Not in Scope of this Requirement
- Die Put-Away-Strategie beim Wareneingang, die einen konkreten Stellplatz vorschlägt (OQ-0015, offen; Gegenstand eines Folge-ADR und einer Folgeanforderung).
- `HandlingUnit` (Gebinde/Paletten-Aggregation über `OnHandRecord`-Zeilen, ADR-0009); Gegenstand einer separaten Anforderung.
- `OnHandRecord`, Bestandsmengen und Bestandszustände (Gegenstand von REQ-0019 und REQ-0020).
- AS/RS-Middleware-Integration; das System speichert lediglich einen Adressstring in `external_ref`, ohne eine externe AS/RS-Schnittstelle zu implementieren.

## Dependencies
- ADR-0009 (Lager-Domänen-Backbone)
- ADR-0001 (WorkspaceScopedModel-Mechanismus)
- UC-0008 (Komponenten-Bestandssuche mit Stellplatz-Anzeige) — nutzt den 4-stufigen Standortpfad als Breadcrumb
