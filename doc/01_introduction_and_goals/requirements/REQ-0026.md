# REQ-0026: Das System löst gescannte Identifikatoren über eine zentrale, priorisierte Auflösungsschicht auf

## Lizenzseite
Open-Source-Backend (`/app/koalixcrm`)

## Quelle
ADR-0016 (Identifier-Registry und Barcode-Auflösung)

## Why
Mehrere Lagerprozesse (Komponentenentnahme, Wareneingang) scannen Barcodes, die gegen
unterschiedliche Identifier-Typen aufgelöst werden müssen. Ohne einen einzigen kanonischen
Auflösungsendpunkt mit fester Priorität würden verschiedene Feature-Teams denselben Code
unterschiedlich interpretieren, und Kollisionen zwischen strukturierten GS1-Codes und freiem
Text blieben unspezifiziert.

## Beschreibung
Der Backend-Dienst stellt einen einzigen kanonischen Endpunkt `POST /api/v1/scan/resolve`
bereit, der einen gescannten Code auflöst und das Zielobjekt mit Typ und ID zurückgibt. Die
Auflösung folgt einer festen, zweistufigen Reihenfolge:

**Stufe 1 — GS1 Application Identifier-Parsing:** Trägt der Code einen erkennbaren GS1-AI-Präfix,
löst das System ausschließlich nach diesem Schema auf: `(01)` GTIN → `ProductVariant` (über
`ProductVariant.gtin`), `(00)` SSCC → `HandlingUnit` (über `HandlingUnit.sscc`), `(01)`+`(21)` SGTIN →
`SerialUnit` (über `SerialUnit.global_uid`), `(8003)` GIAI → `SerialUnit` (über
`SerialUnit.global_uid`), `(414)` GLN → `Location` (über `Location.external_ref`). Wird ein
GS1-AI-Präfix erkannt, läuft ausschließlich diese Stufe; Stufe 2 wird nicht gestartet.

**Stufe 2 — Freier Textabgleich (nur ohne erkanntes GS1-AI-Präfix):** Exact-Match-Suche in
dieser Reihenfolge: `Location.external_ref`, dann `SerialUnit.global_uid`, dann
`ProductVariant.sku`. Der erste Treffer gewinnt.

Die Antwort trägt das Format `{ "kind": "product_variant" | "handling_unit" | "serial_unit" |
"location", "id": "<uuid>", "matched_field": "<Feldname>" }`. Wird derselbe Code in mehr als
einer Entität gefunden (Multi-Hit in Stufe 2), antwortet der Endpunkt mit HTTP 409 und liefert
die Liste der Kandidaten. Kein Treffer ergibt HTTP 404.

Die Auflösung ist auf den Workspace des aufrufenden Benutzers beschränkt, mit Ausnahme von
`ProductVariant.gtin`: GTIN ist katalogweit gültig (nicht workspace-gebunden, ADR-0003, ADR-0016
Nachtrag 2026-07-04); ein GTIN-Treffer liefert eine `ProductVariant`-Referenz ohne impliziten
`OnHandRecord`-Kontext. Alle anderen Identifier-Typen sind workspace-scoped (ADR-0001); die
Freitext-SKU-Auflösung (Regel 3) bleibt workspace-scoped.

## Acceptance Criteria

### AC-1: Endpunkt-Kontrakt
- [ ] `POST /api/v1/scan/resolve` akzeptiert einen Request-Body `{ "code": "<gescannter Barcode-Wert>" }`.
- [ ] Eine Erfolgsantwort (HTTP 200) trägt exakt die Felder `kind`, `id` und `matched_field`.
- [ ] Das Feld `kind` trägt ausschließlich einen der vier Werte `product_variant`, `handling_unit`, `serial_unit`, `location`.

### AC-2: GS1-AI-Auflösung (Stufe 1)
- [ ] Ein erkannter GS1-AI-Präfix `(01)` löst gegen `ProductVariant.gtin` auf.
- [ ] Ein erkannter GS1-AI-Präfix `(00)` löst gegen `HandlingUnit.sscc` auf.
- [ ] Ein erkannter GS1-AI-Präfix `(01)`+`(21)` löst gegen `SerialUnit.global_uid` auf.
- [ ] Ein erkannter GS1-AI-Präfix `(8003)` löst gegen `SerialUnit.global_uid` auf.
- [ ] Ein erkannter GS1-AI-Präfix `(414)` löst gegen `Location.external_ref` auf.
- [ ] Wird ein GS1-AI-Präfix erkannt, wird Stufe 2 (Freitextabgleich) nicht ausgeführt.

### AC-3: Freitextauflösung (Stufe 2)
- [ ] Ohne erkanntes GS1-AI-Präfix prüft das System in der Reihenfolge `Location.external_ref`, `SerialUnit.global_uid`, `ProductVariant.sku`.
- [ ] Der erste Treffer in dieser Reihenfolge gewinnt; nachfolgende Stufen werden nicht mehr geprüft.

### AC-4: Kollisions- und Fehlerbehandlung
- [ ] Liefert die Freitextsuche mehr als einen Treffer für denselben Code, antwortet das System mit HTTP 409 und einer Kandidatenliste im Feld `candidates`.
- [ ] Liefert weder Stufe 1 noch Stufe 2 einen Treffer, antwortet das System mit HTTP 404.

### AC-5: Workspace-Scoping
- [ ] Die Auflösung gegen `SerialUnit.global_uid`, `HandlingUnit.sscc`, `Location.external_ref` und `ProductVariant.sku` ist auf den Workspace des aufrufenden Benutzers beschränkt.
- [ ] Ein automatisierter Test verifiziert, dass diese vier Auflösungspfade keine Treffer aus einem fremden Workspace liefern.
- [ ] Die Auflösung gegen `ProductVariant.gtin` ist katalogweit (nicht workspace-gebunden) und liefert ausschließlich eine `ProductVariant`-Referenz ohne `OnHandRecord`-Kontext.

## Quality Attributes
- **Determinismus**: Die zweistufige Auflösungsreihenfolge liefert für einen gegebenen Code und Workspace-Kontext bei jeder Anfrage dasselbe Ergebnis.
- **Sicherheit**: Workspace-scoped Auflösungspfade liefern unter keinen Umständen Treffer aus einem fremden Workspace; nur `ProductVariant.gtin` ist bewusst katalogweit.

## Affected Components
- Backend: `koalixcrm/stock/services/scan_resolver.py` (GS1-AI-Parser, Freitextabgleich, Kollisionsbehandlung), DRF-View für `POST /api/v1/scan/resolve`
- Frontend: Scan-Eingabemaske in Komponentenentnahme- und Wareneingangs-Workflows (über DRF-Endpunkt; vgl. UC-0009, UC-0010)
- Deployment: keine Infrastrukturänderung

## Not in Scope of this Requirement
- Eine eigenständige `IdentifierRegistry`-Lookup-Tabelle — ADR-0016 lehnt diese Alternative explizit ab; die Auflösung erfolgt über direkte Feldabfragen.
- Eine vollständige GS1-EPCIS-Repository-Implementierung mit ALE/APDL-Endpunkten.
- Nachgelagerte Kontextabfragen (z. B. vollständige `OnHandRecord`-Details nach einem `SerialUnit`-Treffer) — diese erfordern einen zweiten API-Aufruf und sind nicht Bestandteil des Auflösungsendpunkts.
- Eine Auflösung gegen `Product`-Felder für AI `(01)` GTIN oder Freitext-Regel 3: Seit dem ADR-0016-Nachtrag vom 2026-07-04 (OQ-0022 geschlossen) lösen beide Regeln ausschließlich gegen `ProductVariant.gtin` bzw. `ProductVariant.sku` auf; ein direkter `Product`-Auflösungspfad existiert nicht mehr.
