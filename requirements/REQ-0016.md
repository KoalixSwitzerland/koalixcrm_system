# REQ-0016: Das System verwaltet Dienstleistungsprofile als 1:1-Erweiterung von Produkten mit kind=SERVICE

## Lizenzseite
Open-Source-Backend (`/app/koalixcrm`)

## Quelle
ADR-0007 (Dienstleistungsprofil)

## Why
Dienstleistungen unterscheiden sich strukturell von physischen Produkten (kein Gewicht, kein
Lagerbestand, kein Stückliste), benötigen aber ein Abrechnungsmodell, eine Standarddauer und eine
SLA-Referenz. Nullable Dienstleistungsfelder direkt auf `Product` wären semantisch mehrdeutig und
würden kein konsistentes Pflichtfeldflag für Dienstleistungen durchsetzen.

## Beschreibung
`ServiceProfile` (workspace-scoped) steht in einer 1:1-Beziehung zu `Product` und gilt
ausschließlich für Einträge mit `kind = SERVICE`. Das Abrechnungsmodell-Enum umfasst die Werte
`fixed`, `hourly`, `subscription` und `tiered`. Weitere Felder: Standarddauer, Leistungsbeschreibung
und SLA-Referenz.

Die Applikationsschicht erzwingt die Invariante, dass `ServiceProfile` ausschließlich für
`Product` mit `kind = SERVICE` angelegt wird. Workspace-scoped Entitäten erben den
`WorkspaceScopedModel`-Mechanismus: "Tenant-owned data inherits `WorkspaceScopedModel` and is
filtered by `request.active_workspace`" (ADR-0001).

Dienstleistungen nutzen dieselben Preislisten (REQ-0011, REQ-0012), dasselbe Klassifizierungssystem
(REQ-0008, REQ-0009) und dieselben Backbone-Identifikatoren (REQ-0001) wie physische Produkte.

## Acceptance Criteria

### AC-1: Datenbankstruktur
- [ ] `ServiceProfile` trägt einen 1:1-FK auf `Product` (UNIQUE-Constraint auf FK-Feld).
- [ ] `ServiceProfile` trägt ein `billing_model`-Enum mit den Werten `fixed`, `hourly`, `subscription` und `tiered`.
- [ ] `ServiceProfile` trägt ein optionales `default_duration`-Feld (positive Ganzzahl in Minuten).
- [ ] `ServiceProfile` trägt ein `deliverable`-Textfeld als Leistungsbeschreibung.
- [ ] `ServiceProfile` trägt ein optionales `sla_reference`-Feld (Freitext oder URL).

### AC-2: kind-Invariante
- [ ] Das System weist ein `ServiceProfile` ab, dessen zugehöriges `Product` einen `kind`-Wert ungleich `SERVICE` trägt.
- [ ] Die Prüfung der `kind`-Invariante erfolgt in der Applikationsschicht (Serializer-Validator oder Service).
- [ ] Das Anlegen einer `BillOfMaterials` für ein `Product` mit `kind = SERVICE` wird vom System abgewiesen (Querverweis auf REQ-0015 AC-1).

### AC-3: Workspace-Isolation
- [ ] Jede Datenbankabfrage auf `ServiceProfile` filtert automatisch nach `workspace`.
- [ ] Ein automatisierter Test verifiziert, dass `ServiceProfile`-Einträge aus Workspace A nicht in Abfragen aus Workspace B erscheinen.

### AC-4: Einheitliche Katalogliste
- [ ] Ein DRF-Endpunkt für `Product` liefert sowohl Produkte mit `kind = SERVICE` als auch Produkte mit anderen `kind`-Werten in derselben paginierten Liste.
- [ ] Der Listenendpunkt unterstützt einen Filter auf `kind = SERVICE`, der ausschließlich Dienstleistungen zurückgibt.

## Quality Attributes
- **Datenintegrität**: Das Löschen eines `Product` mit `kind = SERVICE` schlägt fehl, wenn noch ein `ServiceProfile`-Eintrag darauf verweist.
- **Erweiterbarkeit**: Das `billing_model`-Enum ist ohne Schema-Änderungen an den abhängigen Modellen erweiterbar (Hinzufügen neuer Enum-Werte erfordert ausschließlich eine Datenbankmigrationen auf `ServiceProfile`).

## Betroffene Komponenten
- Backend: `koalixcrm/products/models/service_profile.py`, kind-Validator, DRF-Serializer und ViewSet
- Frontend: Dienstleistungsprofil-Abschnitt in der Produktdetailansicht, sichtbar nur bei `kind = SERVICE` (über DRF-Endpunkte)
- Deployment: keine Infrastrukturänderung

## Nicht im Scope dieser Anforderung
- Komplexe Projektstrukturierung (Phasen, Meilensteine, Ressourcen) laut ADR-0007.
- SLA-Vertrags-Logik und SLA-Monitoring (Gegenstand eines separaten ADR).
- Abrechnungslogik in Verträgen und Rechnungen (Gegenstand der `contracts`-Anforderungen).
