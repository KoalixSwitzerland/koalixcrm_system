# REQ-0020: Das System berechnet Available-to-Promise aus virtuellen Bestandszuständen und bindet Reservierungen variantengekeyt an kommerzielle Belege

## Lizenzseite
Open-Source-Backend (`/app/koalixcrm`)

## Quelle
ADR-0010 (Lagerbestandszustände und Reservierungen)

## Why
Ohne explizite Zustandsmengen (gebucht, reserviert, disponierbar, in Transit, Quarantäne) führen
einfache Bestandsabfragen zu Über-Kommissionierung, da eine physisch vorhandene Menge gleichzeitig
teilweise für einen Beleg reserviert und teilweise noch disponierbar sein kann.

## Beschreibung
`StockBalance` (workspace-scoped) ist ein denormalisierter Aggregatssatz pro `(workspace, variant,
location)` mit den Mengenfeldern `qty_on_hand`, `qty_booked`, `qty_reserved_for_document`,
`qty_ordered`, `qty_in_transit`, `qty_quarantine` (alle in derselben `uom`). `StockBalance` trägt
einen obligatorischen FK auf `ProductVariant` als autoritativen Schlüssel: „`StockBalance` trägt
einen obligatorischen FK auf `ProductVariant` anstelle des bisherigen FK auf `Product`" (ADR-0010,
Amendment 2026-07-04, autoritative Quelle ADR-0021). Der zusammengesetzte Unique-Constraint
lautet `(workspace, variant, location)`.

Die Available-to-Promise-Formel lautet:

```
ATP = qty_on_hand − qty_booked − qty_reserved_for_document + qty_ordered
```

`qty_in_transit` und `qty_quarantine` gehen nicht in die ATP-Formel ein, da sie nicht
disponierbar sind (ADR-0010). Die Zustandsdefinitionen sind: `on_hand` (physisch verfügbar,
nicht gebunden, in ATP positiv), `booked` (Reserviert ohne Belegbezug, in ATP abgezogen),
`reserved_for_document` (reserviert für einen kommerziellen Beleg, in ATP abgezogen), `ordered`
(eingehend aus Einkaufsauftrag, in ATP positiv), `in_transit` (in Bewegung zwischen Standorten,
nicht in ATP), `quarantine` (QC-Sperre, nicht kommissionierbar, nicht in ATP) — exakt wie in
ADR-0010 benannt.

`StockReservation` (workspace-scoped) ist eine aktive Reservierung einer Menge oder Einzeleinheit
und trägt einen obligatorischen FK auf `ProductVariant`: „`StockReservation` trägt einen
obligatorischen FK auf `ProductVariant` anstelle des bisherigen FK auf `Product`" (ADR-0010,
Amendment 2026-07-04). Sie trägt ferner einen nullable FK auf `Location`, einen nullable FK auf
`Batch`, einen nullable FK auf `SerialUnit`, ein `kind`-Feld (Enum: `SALE`, `RENTAL`,
`PROJECT_HOLD`), ein `reservation_type`-Feld (Enum: `BOOKED`, `RESERVED_FOR_DOCUMENT`), ein
`reservation_status`-Feld (Enum: `PROVISIONAL`, `CONFIRMED`), eine generische Dokumentreferenz
(`document_type` + `document_id`), eine Menge `qty_reserved` (nullable bei serialnummerngebundenen
Reservierungen), einen FK auf `core.Unit`, optionale `rental_start`/`rental_end`-Zeitstempel, ein
`expires_at`-Feld und ein `status`-Feld (Enum: `ACTIVE`, `FULFILLED`, `CANCELLED`, `EXPIRED`).

Für Varianten mit `tracking_mode = SERIAL` gilt zusätzlich zur skalaren ATP-Formel eine
zeitfensterbasierte Verfügbarkeitsprüfung über zwei Funktionen: `is_free(serial_unit, start, end)
-> bool` liefert `true`, wenn keine aktive `StockReservation` mit `kind ∈ {RENTAL, PROJECT_HOLD}`
und `status = ACTIVE` den Zeitraum `[start, end]` schneidet; `free_windows(variant, start, end) ->
list[(serial_unit, [(from, to)])]` liefert für jede `SerialUnit` der Variante die freien
Teilfenster innerhalb `[start, end]` (ADR-0010, Amendment 2026-05-04 OQ-0011, angepasst durch
Amendment 2026-07-04 auf `ProductVariant`). Der zugehörige API-Endpunkt lautet `GET
/api/variants/{id}/serial-units/availability/?start=&end=` (ADR-0010, Amendment 2026-07-04):
„Der API-Endpunkt wechselt entsprechend von `GET
/api/products/{id}/serial-units/availability/?start=&end=` auf `GET
/api/variants/{id}/serial-units/availability/?start=&end=`".

Workspace-scoped Entitäten erben den `WorkspaceScopedModel`-Mechanismus: "Tenant-owned data
inherits `WorkspaceScopedModel` and is filtered by `request.active_workspace`" (ADR-0001).

## Acceptance Criteria

### AC-1: StockBalance-Grundstruktur und ATP-Formel
- [ ] `StockBalance` trägt einen obligatorischen FK auf `ProductVariant`, einen FK auf `Location`, die sechs Mengenfelder `qty_on_hand`, `qty_booked`, `qty_reserved_for_document`, `qty_ordered`, `qty_in_transit`, `qty_quarantine` und einen FK auf `core.Unit`.
- [ ] Der zusammengesetzte Unique-Constraint `(workspace, variant, location)` ist auf Datenbankebene durchgesetzt.
- [ ] Das System berechnet ATP für eine gegebene `(workspace, variant, location)`-Kombination exakt nach der Formel `qty_on_hand − qty_booked − qty_reserved_for_document + qty_ordered`.
- [ ] `qty_in_transit` und `qty_quarantine` fließen in keiner Form in die zurückgegebene ATP-Berechnung ein.

### AC-2: Zustandsdefinitionen
- [ ] Das System stellt exakt die sechs Zustände `on_hand`, `booked`, `reserved_for_document`, `ordered`, `in_transit`, `quarantine` bereit; kein weiterer Zustandswert existiert.
- [ ] Jeder Zustandswert ist eindeutig als „in ATP" oder „nicht in ATP" klassifiziert, exakt entsprechend der Zustandsdefinitionstabelle in ADR-0010.

### AC-3: StockReservation-Grundstruktur
- [ ] `StockReservation` trägt einen obligatorischen FK auf `ProductVariant`, ein `kind`-Feld aus `{SALE, RENTAL, PROJECT_HOLD}`, ein `reservation_type`-Feld aus `{BOOKED, RESERVED_FOR_DOCUMENT}`, ein `reservation_status`-Feld aus `{PROVISIONAL, CONFIRMED}` und ein `status`-Feld aus `{ACTIVE, FULFILLED, CANCELLED, EXPIRED}`.
- [ ] `StockReservation` mit `kind ∈ {RENTAL, PROJECT_HOLD}` trägt einen gesetzten FK auf `SerialUnit`; das System weist eine Zeile mit diesen `kind`-Werten und `serial_unit = null` ab.
- [ ] `StockReservation` mit `kind = SALE` und ohne `SerialUnit`-Bindung trägt `serial_unit = null` und eine gesetzte `qty_reserved`.

### AC-4: Zeitfensterbasierte Verfügbarkeit
- [ ] `is_free(serial_unit, start, end)` liefert `false`, sobald mindestens eine `StockReservation` mit `status = ACTIVE` und `kind ∈ {RENTAL, PROJECT_HOLD}` den angefragten Zeitraum schneidet (zwei halboffene Intervalle `[a, b)` und `[c, d)` schneiden sich, wenn `a < d` und `c < b` gilt).
- [ ] `free_windows(variant, start, end)` liefert für jede `SerialUnit` der Variante die Liste der freien Teilfenster innerhalb `[start, end]`, ausgeschnitten aus allen Belegungsblöcken dieser `SerialUnit`.
- [ ] Der Endpunkt `GET /api/variants/{id}/serial-units/availability/?start=&end=` liefert für jede `SerialUnit` der angegebenen `ProductVariant` den Belegungsstatus (frei / belegt) für den angefragten Zeitraum.
- [ ] Ein Aufruf des veralteten Pfads `GET /api/products/{id}/serial-units/availability/` liefert HTTP 404; der variantengekeyte Endpunkt ist der einzige autorisierte Pfad.

### AC-5: Workspace-Isolation
- [ ] Jede Datenbankabfrage auf `StockBalance` und `StockReservation` filtert automatisch nach `workspace`.
- [ ] Ein automatisierter Test verifiziert, dass `StockBalance`- und `StockReservation`-Einträge aus Workspace A nicht in Abfragen aus Workspace B erscheinen.

## Quality Attributes
- **Datenintegrität**: `StockBalance` wird ausschließlich durch `StockMovement`-Events (REQ-0021) aktualisiert; kein direkter Schreibzugriff auf die Mengenfelder über die API ist möglich.
- **Konsistenz**: Die synchrone Aktualisierung von `StockBalance` im selben Datenbank-Transaktion wie der auslösende `StockMovement`-Eintrag stellt sicher, dass keine ATP-Abfrage einen zwischenzeitlich veralteten Wert liefert.
- **Performance**: Die ATP-Abfrage für eine `(workspace, variant, location)`-Kombination liefert das Ergebnis über einen Index auf diesen Feldern in einer einzigen Tabellenzeile, ohne Aggregation zur Abfragezeit über mehrere `OnHandRecord`-Zeilen.

## Betroffene Komponenten
- Backend: `koalixcrm/stock/models/stock_balance.py`, `stock_reservation.py`, ATP-Berechnungsservice, `is_free`/`free_windows`-Abfragefunktionen, DRF-Serializer und ViewSet, Verfügbarkeits-Endpunkt
- Frontend: ATP-Anzeige in der Bestandsübersicht, Verfügbarkeitskalender für seriennummerngebundene Mietprodukte (über DRF-Endpunkte)
- Deployment: keine Infrastrukturänderung

## Not in Scope of this Requirement
- Die Kopplung des Angebots-Lebenszyklus (DRAFT/SENT/ACCEPTED/…) an `StockReservation`-Übergänge über den generischen Mietfall hinaus; das dieser Anforderung zugrundeliegende ADR-0010 beschreibt bereits die Zustandsmaschine (OQ-0012, geschlossen), die konkrete Verkaufsauftrags-/Angebots-Statusmaschine gehört zur `contracts`-Domäne.
- `RentalAssignment` als Spezialisierung für die physische Übergabephase (Gegenstand einer separaten Mietflotten-Anforderung, ADR-0013).
- Der `StockMovement`-Event-Log, der `StockBalance` aktualisiert (Gegenstand von REQ-0021).
- `OnHandRecord` als granulare Bestandszeile, aus der `StockBalance` aggregiert wird (Gegenstand von REQ-0019).
