# REQ-0007: Das System migriert bestehende ProductType-Daten sicher auf das Product-Modell

## Lizenzseite
Open-Source-Backend (`/app/koalixcrm`)

## Quelle
ADR-0003 (Produkt-Katalog-Backbone, Abschnitt „Negative Consequences"), ADR-0003 Amendment 2026-06-27 (Migrationsstrategie Hybrid-Rename v2.0.0), ADR-0019 (Produkt-`kind`-Invarianten und Gating abhängiger Objekte), ADR-0021 (Produkt-Variantengranularität — Topologie, Schlüsselung und Attribut-Vererbungskaskade)

## Why
Die Umbenennung `ProductType` → `Product` bricht FK-Referenzen aus `contracts` und `accounting`
auf die Tabelle `crm_producttype`. Eine fehlgeschlagene oder unvollständige Migration führt zu
Datenverlust und defekten Vertragsreferenzen in Produktionssystemen.

## Beschreibung
Das System stellt eine Datenmigration bereit, die alle bestehenden `ProductType`-Zeilen in das
neue `Product`-Schema überführt und alle FK-Referenzen aus `contracts` und `accounting` auf die
neue Tabelle umschreibt. Die Migration ist idempotent und reversibel.

Die Migrationsstrategie ist durch ADR-0003 Amendment 2026-06-27 entschieden: eine einzige
additive Django-Migration mit `SeparateDatabaseAndState` benennt `crm.ProductType` in
`products.Product` um und verschiebt das Modell in die `products`-App; der DB-Operator führt
`ALTER TABLE crm_producttype RENAME TO products_product` aus. Da Primary Keys unverändert
bleiben, folgen In-Datenbank-FK-Constraints aus `contracts` und `accounting` dem Rename
automatisch ohne Zeilen-Rewrite. Die leere `Product`-Shell-Klasse entfällt in derselben
Migration; eingehende FKs auf die Shell werden auf `ProductVariant` umgeleitet. Die Migration
ist rückwärts ausführbar und wird als Breaking v2.0.0-Schnitt ausgeliefert.

Dieselbe Migration legt für jedes migrierte `Product` genau eine `ProductVariant` als
Default-Variante an, die den früheren Identifikator und die frühere `sku` des `ProductType`
übernimmt (ADR-0021: „jedes `Product` besitzt ≥1 `ProductVariant`"; „`sku` | `ProductVariant` |
Lagerhaltungsnummer ist variantenspezifisch"). Die Migration schreibt den FK jeder bestehenden
`ProductPrice`-Zeile von `Product` auf diese eine Default-`ProductVariant` um; der Zeileninhalt
(Betrag, Währung, Gültigkeitszeitraum, Preisliste) bleibt unverändert, nur das
Referenzobjekt wechselt (ADR-0021, per ADR-0005 Amendment 2026-06-28: „`ProductPrice` trägt
einen FK auf `ProductVariant` (nicht auf `Product`)").

## Acceptance Criteria

### AC-1: Vollständigkeit
- [ ] Nach Ausführung der Migration existiert für jede frühere `ProductType`-Zeile genau eine `Product`-Zeile mit identischen Stammdaten.
- [ ] Kein `ProductType`-Datensatz geht bei der Migration verloren (Zeilenzahl-Invariante: `COUNT(Product) >= COUNT(ProductType_vor_Migration)`).

### AC-2: FK-Integrität
- [ ] Alle FK-Referenzen aus `contracts` auf die frühere `crm_producttype`-Tabelle zeigen nach der Migration auf die neue `products_product`-Tabelle.
- [ ] Alle FK-Referenzen aus `accounting` auf die frühere `crm_producttype`-Tabelle zeigen nach der Migration auf die neue `products_product`-Tabelle.
- [ ] Kein bestehender Vertrag und kein bestehendes Buchhaltungsdokument verliert seinen Produktbezug.
- [ ] Die FK-Constraints folgen dem Rename ohne Zeilen-Rewrite; kein einzelner FK-Wert wird manuell umgeschrieben (Mechanismus: unveränderte Primary Keys + `ALTER TABLE`-Rename, ADR-0003 Amendment 2026-06-27).
- [ ] Alle eingehenden FKs auf die leere `Product`-Shell-Klasse sind nach der Migration auf `ProductVariant` umgeleitet; keine FK-Referenz auf die Shell bleibt unaufgelöst.

### AC-3: Idempotenz und Reversibilität
- [ ] Die Migration verwendet `SeparateDatabaseAndState`: der State-Operator benennt `crm.ProductType` → `products.Product` um und verschiebt das Modell; der DB-Operator führt `ALTER TABLE crm_producttype RENAME TO products_product` aus.
- [ ] Die Migration ist idempotent: eine zweite Ausführung verändert den Datenbankzustand nicht.
- [ ] Ein Management-Command führt eine Dry-Run-Prüfung durch, die vor der eigentlichen Migration Zeilenzahlen und FK-Konsistenz meldet.
- [ ] Die Migration ist rückwärts ausführbar (backward migration); das Ergebnis ist der Zustand vor der Migration.

### AC-4: Default-ProductVariant und ProductPrice-FK-Umschreibung
- [ ] Für jedes migrierte `Product` existiert nach der Migration genau eine `ProductVariant` (Default-Variante), die den früheren Identifikator und die frühere `sku` des `ProductType`-Datensatzes trägt.
- [ ] Jede `ProductPrice`-Zeile, die vor der Migration auf ein migriertes `Product` verwies, verweist nach der Migration auf dessen Default-`ProductVariant`.
- [ ] Die Zeilenzahl von `ProductPrice` bleibt durch die Migration unverändert (Zeilenzahl-Invariante: `COUNT(ProductPrice)_nach = COUNT(ProductPrice)_vor`).
- [ ] Kein inhaltliches Feld einer `ProductPrice`-Zeile (Betrag, Währung, `valid_from`, `valid_to`, Preisliste) wird durch die FK-Umschreibung verändert.

### AC-5: kind-Standardwert
- [ ] Jeder migrierte `Product`-Datensatz trägt einen `kind`-Wert; kein migrierter Datensatz hat `kind = NULL`.
- [ ] Der Standard-`kind` für `ProductType`-Zeilen ohne Brancheninformation ist `TRADING_GOOD`.
- [ ] Die Django-Migrationsdatei dokumentiert den gewählten Standard-`kind` (`TRADING_GOOD`) explizit als Kommentar.
- [ ] `kind` bleibt für jeden migrierten Datensatz editierbar, solange sein Sperr-Set leer ist — d. h. solange kein `ServiceProfile`, `BillOfMaterials`, keine Lagerentität und kein sonstiges Element des Sperr-Sets aus ADR-0019 für dieses Produkt existiert: „`kind` ist frei änderbar, solange kein Element des folgenden Sperr-Sets existiert." (ADR-0019, Abschnitt „kind-Unveränderlichkeit").

## Quality Attributes
- **Sicherheit**: Die Migration wird auf einem produktionsnahen Datenabzug probeweise ausgeführt, bevor sie auf Produktionsdaten angewendet wird.
- **Datenintegrität**: Der Dry-Run-Management-Command meldet alle FK-Verletzungen, bevor die Migration ausgeführt wird.

## Betroffene Komponenten
- Backend: Django-Datenmigration (`RunPython`), Management-Command für Dry-Run, Modelle in `contracts` und `accounting`
- Deployment: keine Infrastrukturänderung; der DBA führt die Migration in einem Wartungsfenster oder im Rahmen des Deployments aus

## Nicht im Scope dieser Anforderung
- Eine phasenweise oder Dual-Stack-Migrationsstrategie (kein langgelebter paralleler Betrieb beider Modelle; die Strategie ist durch ADR-0003 Amendment 2026-06-27 auf den einmaligen v2.0.0-Schnitt festgelegt).
- Inhaltliche Migration von `customer_group_transform` (dieses Modell wird gemäß ADR-0005 unverändert beibehalten).
- Migration des `ProductPrice`-Zeileninhalts selbst (Betrag, Währung, Gültigkeitszeitraum, Preisliste bleiben unverändert; ADR-0005). Diese Anforderung deckt ausschließlich die FK-Umschreibung von `Product` auf die neu angelegte Default-`ProductVariant` ab (AC-4), nicht die Modellierung von `ProductPrice` selbst.
