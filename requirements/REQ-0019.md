# REQ-0019: Das System führt variantengekeyte Lagermengen als atomare Bestandszeilen mit Eindeutigkeitsgarantie und Bewegungskonsistenz

## Lizenzseite
Open-Source-Backend (`/app/koalixcrm`)

## Quelle
ADR-0009 (Lager-Domänen-Backbone), ADR-0021 (Produkt-Variantengranularität)

## Why
Ohne eine atomare, eindeutig schlüsselbare Bestandszeile pro Variante, Standort und
Chargen-/Serienreferenz sind weder FEFO-Picklisten noch eine korrekte Mehrfachlagerung derselben
Variante an verschiedenen Standorten zuverlässig abbildbar; die Schlüsselung muss auf
`ProductVariant` erfolgen, da dies der autoritative Bestands-Schlüssel des Systems ist.

## Beschreibung
`OnHandRecord` (workspace-scoped) ist eine atomare Lagermengenzeile. Sie trägt einen
obligatorischen FK auf `ProductVariant` als primären, autoritativen Lager-Schlüssel: „`OnHandRecord`
trägt einen FK auf `ProductVariant` als primären, obligatorischen Lager-Schlüssel. Der bisherige
obligatorische FK auf `Product` entfällt als direktes Feld auf `OnHandRecord`; das Produkt ist
über den FK-Pfad `OnHandRecord → ProductVariant → Product` erreichbar" (ADR-0009, Amendment
2026-06-28, autoritative Grundlage ADR-0021). `OnHandRecord` trägt ferner einen FK auf `Location`
(REQ-0018), einen nullable FK auf `Batch` und einen nullable FK auf `SerialUnit` (REQ-0022), einen
`owner_type` (Enum: `OWN`, `CUSTOMER_CONSIGNMENT`, `RENTAL`), einen nullable FK auf `Party` für
Fremdbestand, eine Mengenspalte `qty_on_hand` und einen FK auf `core.Unit` als Mengeneinheit.

Der zusammengesetzte Unique-Constraint lautet: `(workspace, variant, location, batch,
serial_unit, owner_type, owner_party)` (ADR-0009, Amendment 2026-06-28).

`OnHandRecord` enthält keine aggregierten Zustandsmengen (gebucht, reserviert, disponierbar); die
Aufteilung in Zustandsmengen ist Gegenstand von REQ-0020. Jede Mengenänderung an `OnHandRecord`
entsteht ausschließlich als Konsequenz eines `StockMovement`-Eintrags mit `qty != null` (REQ-0021):
„`StockMovement`-Events mit `qty != null` aktualisieren `StockBalance`-Felder ... synchron im
selben Datenbank-Transaktion" (ADR-0011); dieselbe synchrone Aktualisierungsregel gilt für
`OnHandRecord`, aus dem `StockBalance` aggregiert wird. Ein negativer `qty_on_hand`-Wert ist
ausgeschlossen, mit Ausnahme des Falls, in dem eine Mengeneingabe explizit den verfügbaren
Bestand überschreitet und der Benutzer die Buchung bewusst bestätigt; in diesem Fall setzt das
System `qty_on_hand` auf den Wert `0` statt eines negativen Werts.

Workspace-scoped Entitäten erben den `WorkspaceScopedModel`-Mechanismus: "Tenant-owned data
inherits `WorkspaceScopedModel` and is filtered by `request.active_workspace`" (ADR-0001).

## Acceptance Criteria

### AC-1: OnHandRecord-Grundstruktur
- [ ] `OnHandRecord` trägt einen obligatorischen FK auf `ProductVariant`, einen obligatorischen FK auf `Location`, einen nullable FK auf `Batch`, einen nullable FK auf `SerialUnit`, einen `owner_type`-Wert aus `{OWN, CUSTOMER_CONSIGNMENT, RENTAL}`, einen nullable FK auf `Party`, eine Dezimalmenge `qty_on_hand` und einen FK auf `core.Unit`.
- [ ] `OnHandRecord` trägt keinen direkten FK auf `Product`; das Produkt ist ausschließlich über den FK-Pfad `OnHandRecord → ProductVariant → Product` erreichbar.
- [ ] `owner_type = CUSTOMER_CONSIGNMENT` oder `owner_type = RENTAL` erfordert einen gesetzten `owner_party`-FK; das System weist eine Zeile mit diesen `owner_type`-Werten und `owner_party = null` ab.

### AC-2: Eindeutigkeitsconstraint
- [ ] Das System erzwingt den zusammengesetzten Unique-Constraint `(workspace, variant, location, batch, serial_unit, owner_type, owner_party)` auf Datenbankebene.
- [ ] Eine zweite `OnHandRecord`-Zeile mit identischer Kombination aus `workspace`, `variant`, `location`, `batch`, `serial_unit`, `owner_type` und `owner_party` wird vom System abgewiesen.
- [ ] Zwei `OnHandRecord`-Zeilen derselben `ProductVariant` an unterschiedlichen `Location`-Werten sind gleichzeitig gültig.

### AC-3: Konsistenz mit dem Bewegungslog
- [ ] Jede Änderung von `OnHandRecord.qty_on_hand` entsteht ausschließlich durch einen zugehörigen `StockMovement`-Eintrag (REQ-0021) mit `qty != null`; kein direkter Schreibzugriff auf `qty_on_hand` ohne begleitenden `StockMovement`-Eintrag ist über die API möglich.
- [ ] Die Summe aller `StockMovement`-Mengenänderungen (Zugänge minus Abgänge) für eine gegebene Kombination aus `ProductVariant`, `Location`, `Batch`/`SerialUnit`, `owner_type` und `owner_party` ergibt exakt den aktuellen `qty_on_hand`-Wert der zugehörigen `OnHandRecord`-Zeile.
- [ ] Ein automatisierter Konsistenztest rekonstruiert `qty_on_hand` durch Aggregation des `StockMovement`-Logs und vergleicht das Ergebnis mit dem gespeicherten `OnHandRecord`-Wert für eine Stichprobe von Kombinationen.

### AC-4: Keine negativen Bestände
- [ ] Das System weist eine Buchung ab, die `qty_on_hand` auf einen negativen Wert setzen würde, außer der Benutzer bestätigt die Buchung explizit trotz Mengenüberschreitung.
- [ ] Bei expliziter Bestätigung setzt das System `qty_on_hand` auf `0` statt auf einen negativen Wert; der zugehörige `StockMovement`-Eintrag trägt `reason_code = quantity_exceeded`.
- [ ] `qty_on_hand = 0` ist ein gültiger Zustand und löst keine automatische Löschung der `OnHandRecord`-Zeile aus.

### AC-5: Workspace-Isolation
- [ ] Jede Datenbankabfrage auf `OnHandRecord` filtert automatisch nach `workspace`.
- [ ] Ein automatisierter Test verifiziert, dass `OnHandRecord`-Einträge aus Workspace A nicht in Abfragen aus Workspace B erscheinen.

## Quality Attributes
- **Datenintegrität**: Der zusammengesetzte Unique-Constraint `(workspace, variant, location, batch, serial_unit, owner_type, owner_party)` ist auf Datenbankebene durchgesetzt, nicht ausschließlich in der Applikationsschicht.
- **Konsistenz**: `OnHandRecord.qty_on_hand` weicht zu keinem Zeitpunkt von der Summe der zugehörigen `StockMovement`-Mengenänderungen ab, da beide synchron in derselben Datenbank-Transaktion aktualisiert werden (ADR-0011).
- **Performance**: Eine Bestandsabfrage nach `(workspace, variant, location)` liefert das Ergebnis über einen Index auf diesen Feldern, ohne Tabellen-Scan bei 10 Millionen+ Lagereinheiten.

## Betroffene Komponenten
- Backend: `koalixcrm/stock/models/on_hand_record.py`, DRF-Serializer und ViewSet, Bewegungsbuchungs-Service (gemeinsam mit REQ-0021)
- Frontend: Bestandsanzeige je Standort und Variante in der Lagerbestandsübersicht (über DRF-Endpunkte)
- Deployment: Datenmigration für den zusammengesetzten Unique-Constraint bei Bestandseinführung

## Not in Scope of this Requirement
- Zustandsmengen (gebucht, reserviert, disponierbar, in Transit, Quarantäne) und die ATP-Formel (Gegenstand von REQ-0020).
- Der `StockMovement`-Event-Log selbst, seine Feldstruktur und Unveränderlichkeit (Gegenstand von REQ-0021).
- `Batch`- und `SerialUnit`-Entitäten sowie `tracking_mode` (Gegenstand von REQ-0022).
- `HandlingUnit`-Aggregation über mehrere `OnHandRecord`-Zeilen (Gegenstand einer separaten Anforderung).
- Produktweite Bestandsübersichten über mehrere Varianten hinweg; diese erfordern eine GROUP-BY-Aggregation über den FK-Pfad `OnHandRecord → ProductVariant → Product` und sind nicht über ein direktes FK-Feld auf `OnHandRecord` abfragbar (ADR-0009, Amendment 2026-06-28).
