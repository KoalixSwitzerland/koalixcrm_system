# REQ-0002: Das System strukturiert Produkte in Familien und Varianten

## Lizenzseite
Open-Source-Backend (`/app/koalixcrm`)

## Quelle
ADR-0003 (Produkt-Katalog-Backbone)

## Why
Für Multi-Tenant-Plattformen mit 10 000+ SKUs muss die Identifikation auf SKU-Ebene sauber von
den Stammdaten getrennt sein. `ProductFamily` gruppiert eine Produktlinie; `ProductVariant` hält
eine Zeile pro tatsächlicher SKU mit Varianten-Achsen-Werten.

## Beschreibung
`ProductFamily` (workspace-scoped) fasst thematisch verwandte `Product`-Objekte zu einer Linie
zusammen. Sie trägt einen Namen und ist dem `workspace` zugeordnet. Alle `Product`-Objekte einer
`ProductFamily` tragen denselben `kind`-Wert; diese Invariante setzt `ProductKindPolicy`
(ADR-0019) in der Applikationsschicht durch.

`Product` (workspace-scoped) ist das abstrakte Katalogobjekt. Es trägt einen optionalen FK auf
`ProductFamily` und besitzt ≥1 `ProductVariant`.

`ProductVariant` (workspace-scoped) repräsentiert eine einzelne handelbare SKU. Sie trägt einen
FK auf `Product` (nicht auf `ProductFamily`). Varianten-spezifische Attributwerte werden als
Zeilen mit gesetztem `variant_id` in den getypten EAV-Wertetabellen gespeichert; der effektive
Attributwert löst sich zur Lesezeit nach der Kaskade Varianten-Override → Produkt-Wert →
Familie-/AttributeSet-Standard auf (Option A, ADR-0021). Workspace-scoped Entitäten erben den
`WorkspaceScopedModel`-Mechanismus: "Tenant-owned data inherits `WorkspaceScopedModel` and is
filtered by `request.active_workspace`" (ADR-0001).

## Acceptance Criteria

### AC-1: ProductFamily-Grundregeln
- [ ] Jede `ProductFamily` gehört zu genau einem Workspace.
- [ ] Jede Datenbankabfrage auf `ProductFamily` filtert automatisch nach `workspace`.
- [ ] Der Name einer `ProductFamily` ist innerhalb eines Workspace eindeutig.

### AC-2: ProductVariant-Grundregeln
- [ ] Jede `ProductVariant` trägt einen FK auf `Product` (ADR-0021: "`ProductVariant` trägt einen FK auf `Product` (nicht auf `ProductFamily`)").
- [ ] Die Kombination `(workspace, sku)` ist über alle `ProductVariant`-Objekte eindeutig.
- [ ] Eine `ProductVariant` ohne FK auf ein existierendes `Product` wird vom System abgewiesen.

### AC-3: Varianten-Attributwerte (Option A, ADR-0021)
- [ ] Varianten-spezifische Attributwerte werden als Zeilen mit `variant_id = <variante>` in den getypten EAV-Wertetabellen (`ProductAttributeDecimal`, `ProductAttributeString`, `ProductAttributeEnum`, `ProductAttributeBool`, `ProductAttributeReference`, `ProductAttributeInt`) gespeichert.
- [ ] Eine Zeile mit `variant_id IS NULL` in einer EAV-Wertetabelle gilt als Produkt-Wert; die Abwesenheit einer Zeile mit `variant_id = <variante>` für eine gegebene Attributdefinition bedeutet INHERIT und delegiert an den nächsten Kaskadenschritt.
- [ ] Der effektive Attributwert einer `ProductVariant` wird zur Lesezeit nach der Kaskade Varianten-Override → Produkt-Wert → Familie-/AttributeSet-Standard aufgelöst; kein materialisierter Effektivwert wird in der Datenbank vorgehalten.
- [ ] Ein `variant_id`-Override-Wert ist immer ein konkreter, nicht-null Domänenwert.
- [ ] Zwei `ProductVariant`-Objekte desselben `Product` mit identischen Varianten-Achsen-Attributwert-Kombinationen werden vom System abgewiesen.

### AC-4: Workspace-Isolation
- [ ] Ein automatisierter Test verifiziert, dass `ProductFamily`- und `ProductVariant`-Objekte aus Workspace A nicht in Abfragen aus Workspace B erscheinen.

## Quality Attributes
- **Skalierung**: Das System unterstützt mindestens 100 `ProductVariant`-Einträge pro `ProductFamily` ohne Degradation der Listenabfrage.
- **Datenintegrität**: Das Löschen einer `ProductFamily` schlägt fehl, wenn noch `Product`-Objekte mit FK auf sie existieren (referentielle Integrität; `ProductVariant` trägt keinen direkten FK auf `ProductFamily`).

## Betroffene Komponenten
- Backend: `koalixcrm/products/models/product_family.py`, `product_variant.py`, zugehörige Serializer und ViewSets
- Frontend: Variantenauswahl in Produktdetail- und Listenansicht (über DRF-Endpunkte)
- Deployment: keine Infrastrukturänderung

## Nicht im Scope dieser Anforderung
- Die interne Darstellung von Varianten-Achsen im Frontend-UI (Gegenstand der Frontend-Anforderungen).
- Preislogik auf Variantenebene (Gegenstand von REQ-0010, ADR-0005).
